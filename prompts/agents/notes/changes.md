# Change notes
- The statements on carrying a change to the code or the documents from who writes it to its commit, that more than one entry point inlines or links.

## Changes

### Carrying a change
- Have an editor write each change to the code or the documents. The `handbook-expanded` agent writes the part of a change in [lib.dl](programs/lib.dl), in the modules under [lib](programs/lib) and in the solvers under [solvers](programs/solvers), with the accepted gate outputs its items change, and a code editor in the same worktree writes the part under [src](src) or [scripts](scripts).
- A change is one editor's edit, or one edit for each part the line above splits it into, and each edit that fixes what its review or its checks found.
- A change passes when each code editor and each `handbook-expanded` editor that worked on it reports done or blocked, when no item its editors report done needs an item they report unfinished, and, where it changes the documents, the `///` and `//!` comments of [lib.dl](programs/lib.dl) and of the modules under [lib](programs/lib) among them, when a reply of the doc reviewer that follows the last edit of those changes says no finding stands and `uv run python -m controlled_markdown check` passes in its worktree.
- Send the findings of a change's checks to the editor that made the change, with SendMessage. A change's reviewer sends its findings to the change's editors, and each editor sends its fixes to that reviewer: relay none of them. Launch a fresh reviewer only for a change's first review, and for the next review of a change you take up whose reviewer another agent launched.
- Where the `controlled_markdown` check reports a `quotes` call that a change to the documents broke, send that finding to a code editor in place of the doc editor: launch one in the change's worktree, with each call the check reports as an item, to repair as [Prose in code](src/controlled_markdown/writing.md#prose-in-code) gives, and the files of those calls as the files it may edit.
- Where a doc reviewer's reply gives a finding outside its `Held back` heading, launch an editor in the change's worktree, and send its agent id to that reviewer with SendMessage. For a finding on a line of the document set or on one of those comments, launch a doc editor, with a brief of the form [Briefs](prompts/agents/notes/launching.md#briefs) gives, whose Intent, where the change has no ticket, says what that line's readers need to know, taken from the items of the change's briefs. For a finding on prose in code, launch a code editor, with the correction of the finding's line as its item and the finding's file as the file it may edit.
- Launch the first editor of a change with the Agent tool's `isolation: "worktree"`, and take the change's worktree from the Agent tool's completion notification for that editor.
    - The harness removes that worktree, with its untracked files, when that editor ends a turn with no change to a tracked file. Launch the editor that continues such a change as a new first editor, and send no editor to a worktree you add yourself.
        * comment: A code editor whose first worktree was removed after a turn with no edit had no worktree to continue in, and its notes under `.scratch/` were gone: ticket `1791209231-worktree-cleanup-operator-1`. The operator then sent that editor to a worktree it added with `git worktree add`, and the permission classifier refused the editor's edits to [src](src) and [scripts](scripts) there: ticket `1791209668-classifier-refusal-operator-1`.
- Give that worktree, by its path, in the brief of each later agent that works on the change.
- Where you take up a change whose worktree, given by your brief, a message or its ticket's log, stands, and whose editors another agent launched, continue it in that worktree in place of launching a first editor. Wait until `uv run python scripts/profile_runs.py --running <id>`, with that other agent's id from your brief, a message or its ticket's log, lists no agent whose launch description or calls show it works on the change: run a command whose loop repeats it until then, led by `: 'unattended-wait: <the agents you wait on>';`. Then launch there a new editor for each part of the change, and send no message to an editor or reviewer that other agent launched.
- Run the changes you launch at the same time.

### Findings an editor leaves
- Judge each finding a change's editor leaves with a reason against the change's worktree, that reason, and [The ladder](prompts/agents/notes/decisions.md#the-ladder): keep it only where it is so, acting on it serves a rung, and no decision already made rules it out. Record each finding you drop, with its reason, in your reply, and send the editor each you drop, as dropped, and each you keep that needs no decision, as kept, each with your reason.
- Where the editor leaves a finding, or an item unfinished, for a decision, decide the question it raises, from the reason the editor gives, as [How a decision is made](prompts/agents/notes/decisions.md#how-a-decision-is-made) gives, and send the editor the decision.

### Merging a change
- Where a kept finding of a change raises a decision that goes to the user, leave that change unmerged, and give its branch and worktree with that decision in your reply. The session that gets the user's ruling, or carries out that decision's default, merges the change.
- Before you merge a change, read the diff of each accepted gate output its briefs list, and send each difference there that those briefs do not ask for to the change's editor as a finding of its checks.
- Merge a change only once it passes, with `uv run python scripts/merge_change.py <worktree> -m <message>`, and commit in no other way.
- Where that script exits with status 1, leave the worktree as it is. Where it reports that the rebase conflicts, run the change again with a new first editor, and give the old worktree and its branch in your reply. Where it reports a failed check, send what it reports to the change's editor as a finding of its checks. Otherwise, give the worktree and the script's message in your reply.
    - Where the failed check is the gate, give in that finding, for each `DIFF` line that the change's briefs ask for, the accepted output under `tests/gate/accepted/` to update.
- Where the harness or the permission classifier denies the merge call, give the worktree in your reply with the merge as unfinished.
- Once a change is merged, move to `tickets/closed/` its ticket, then each `question` ticket filed on it that still stands outside `tickets/closed/`, with `fixed`, the change's number and the hash `master` stands at after the merge as the note.
- Once a change is merged, close each `refactor` ticket outside `tickets/closed/` whose title ends in `many ideas in one place` and cites a module that a code editor of the change reports it split, with `fixed`, the change's number where it has a ticket, and the hash `master` stands at after the merge as the note. Where that report gives a part of the module as left unsplit, write that part as a log line on the ticket in place of closing it.

### A merge an agent was denied
- Where you run the merge of a change whose merge call an agent you launched gave as denied, and your merge is denied too, move the change's ticket to `tickets/blocked/`, with a note that opens with `user` and gives the call, the denial's text and the worktree. Where your merge goes through, send the change to an operator for its [After a batch](prompts/agents/operator.md#after-a-batch): to an operator that runs, or in the brief of the next one you launch.

## budget
- Do each step your documents give, and finish the work, even where it runs past the budget a `Budget: N minutes` line of your brief or a later message gives.

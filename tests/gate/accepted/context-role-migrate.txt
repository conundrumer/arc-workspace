Your message is a brief, or a role and then its brief. A role is the text of a file under `prompts/roles/`, as `uv run python scripts/context.py role <stem>` prints it below its first line. Where your message opens with a role, follow the role, and take the rest of the message as its brief.

- `uv run python scripts/context.py section '<chapter>#<heading>'` prints a whole section.
    - The target of a link into `docs/handbook/` also works as the argument.
- A bare task id cites a solver that works out the statement it sits under, and this rendering leaves out the line saying what that solver shows.
- The same command prints the section with those lines, under the heading the id sits below.
- Where your instructions, your brief or a later message ask you to file an issue, file it with `uv run python scripts/file_issue.py`, in the form its `--help` gives.
    - Where no other line gives them, `<agent>` is your agent's name, and `<source>` is a short name for your work.
    - Where no other line gives an issue's kind, give it one of these:
        - `interference`: something in your output was wrong because of the issue, whether or not you repaired it.
        - `delay`: the issue cost time or tokens only.
        - `undecided`: a case your rules do not cover, or a place that poses a question.
    - Write under `Evidence` the line quoted, or the command and its output, or the grid, as you saw it.
    - Leave out what the fix should be.

# Handbook

## Principles

### The goal

- The corpus supports the synthesis of solver programs, and takes as much as it can from each task, in this order:
    - **Concept.** A solver has a case for the concept.
    - **Coverage.** A solver has a case for each other model that meets the case conditions.

### Definitions

#### The solver's parts

- **parameter**: a relation whose facts are stored rather than derived.
- **derived data**: a relation derived by a clause.
- **parameterization**: the parameters together with the values each one takes across the generator's tasks.
    - Θ = ∏ᵢ Θᵢ
        - Θᵢ: the values parameter i takes across the generator's tasks
            - A parameter's type is its encoding, and a value of the type that no task gives is outside Θᵢ.
        - θ ∈ Θ: an assignment
- **assignment**: one choice of value for each parameter.
- **program**: the clauses that derive `out` from `in` and the parameters.
- **lookup table**: a parameter that maps keys from the input to entries that the program uses.

#### Models and tasks

- **model**: the function that gives the output grids for an assignment and an input grid.
    - M : Θ × G → 𝒫(G)
        - G: the set of grids
    - A model is defined at an assignment and input when its output is nonempty and contains only total grids.
- **evidence**: a task's train pairs and test inputs.
    - D(T) = (train(T), test_in(T))
- **solver**: one or more models of a task.
    - For each model, the solver stores an assignment determined by the evidence.
        - S_M = (M, stored_M)
            - stored_M : D(T) ↦ θ, the assignment the determination derives from the evidence
- **determination**: the clauses that derive a stored value from the evidence.
    - Test outputs are held out, so two tasks with identical evidence receive the same stored assignment.
        - D(T) = D(T′) ⇒ stored_M(D(T)) = stored_M(D(T′))
- **tiebreak**: content that the task leaves free.
- **candidate**: a set of a pair's accepted outputs that differ only in a tiebreak.
    - Outputs in different candidates differ by more than a tiebreak.
    - A pair has at most two candidates.
- **split task**: a task formed by choosing one candidate at each pair that has two.
    - Each such pair in the resulting task accepts only the chosen candidate.
    - alts(T): the set of split tasks of T
- **fit**: a model fits a split task at an assignment when its output on each pair's input is that pair's candidate, including for the test pairs.
    - M(θ) ⊨ T ⇔ ∀(x, Y) ∈ pairs(T). M(θ, x) = Y
        - pairs(T) = train(T) ⧺ zip(test_in(T), test_out(T))
    - A model fits a task when it fits one of that task's split tasks.
- **model family**: all tasks that a model fits under some assignment.
    - fam(M) = {T | ∃T′ ∈ alts(T). ∃θ ∈ Θ. M(θ) ⊨ T′}
- **sibling task**: another task in the family of this task's model.
- **peer model**: another model whose family contains this task.
- **hypothesis**: the assertion that a task belongs to a model's family.
- **case**: one model in the solver, together with its hypothesis.

#### The generator

- **generator**: the process that produces the task and other tasks.
- **variant task**: a task the generator produces.
- **task data**: a value that differs between this task and a variant task the model fits.
    - The program fixes no task data.
- **invariant of the inputs**: a regularity satisfied by every input in the evidence.
    - An invariant of the inputs is an estimate of a constraint the generator applies in this task.

#### The concept

- **claim**: a statement about the task, of one of these kinds:
    - **scene claim**: what every input contains.
        - A scene claim is an invariant of the inputs.
    - **rule**: what the output takes from the input.
- **concept**: what a person takes the task to be an instance of.
    - **concept statement**: the claims that express the concept.
- **concept case**: the case whose model the concept statement describes.

#### Choice points and open parameters

- **choice point**: an undetermined property whose possible answers are models represented by cases.
    - A choice point stands at the concept, or under a branch when its property exists only with that branch.
        - When the property exists with several branches of a point, those branches form one branch of it, and the choice among them is a point under that branch.
        - When the property exists only with a combination of branches of different points, the point stands under one of those branches.
    - **branch**: one possible answer to a choice point.
        - The **concept branch** at a choice point is the branch taken by the claims the point stands under.
        - Each case takes one branch at each choice point at the concept, and at each under a branch it takes.
        - A branch's model takes that branch, and the concept branch at every other choice point it takes.
        - A branch's cases are the cases that take it.
- **open parameter**: an undetermined property whose possible answers are values of one parameter, with the program unchanged.
    - **open values**: the values of that parameter that a reader of the concept could take, and that the pairs do not separate.
    - A sibling task containing an input on which the open values disagree fixes the parameter to one of those values.

#### Witnesses

- **divergence witness**: an input on which one of these holds:
    - at some assignment, two models give different outputs, or one is defined and the other is not.
    - a model's output at some assignment differs from the output the generator pairs with the input.
    - A branch's witnesses are divergence witnesses between its model and the concept branch's model.
    - A witness stands at this task's stored assignment when the model it is for is defined there and differs there from what it is separated from. Otherwise it stands at the assignment that changes the fewest of that model's parameters and at which that holds, and at the stored assignment when there is none.
        - The model a witness is for is the branch's model for a branch's witness, the concept case's model for a witness of the concept case, and the case's model for a witness without which a case fails Equivalence or Subsumption.
    - A witness breaks a scene claim when the concept case's claim, read at the assignment the witness stands at, is false of it.
    - An output identical to the input is still defined, so a divergence at such an output is valid.
        - 41e4d17e
- **annotator**: whoever judges a witness.
- **plausibility**: the annotator's ordinal estimate of how readily the generator could produce the witness. Its value is the first applicable level:
    - `ordinary`: readily, breaking no scene claim of the concept case.
        - 3b4c2228
    - `variant`: routinely, in a variant task.
        - 3b4c2228
    - `borderline`: only under unusual conditions.
    - `foreign`: never.
        - 00dbd492
- **verdict**: the annotator's judgment of the output that the generator would pair with the witness.
    - `concept`: the concept case's output.
    - the branch's name: the output of that branch's model.
    - `any`: the output of any case defined on the witness.
    - `other`: an output that no case produces.

#### Equivalence and subsumption

- Two models are equivalent when each assignment of either has an assignment of the other that it agrees with.
    - Equivalent(A, B) ⇔ (∀θ ∈ Θ. ∃φ ∈ Θ′. Agree(θ, φ)) ∧ (∀φ ∈ Θ′. ∃θ ∈ Θ. Agree(θ, φ))
    - Two assignments agree when, on every input, the two models give the same output or neither is defined.
        - Agree(θ, φ) ⇔ ∀x ∈ G. A(θ, x) = B(φ, x) ∨ (¬Def_A(θ, x) ∧ ¬Def_B(φ, x))
            - Def_M(θ, x): M is defined at θ and x
- Agreement on every input in the current task does not establish equivalence between models.
    - 3b4c2228
- Agreement on every input the generator produces does not establish equivalence either: the comparison ranges over every input.
    - 00dbd492
- An assignment that agrees with no assignment of the other model refutes equivalence, and a divergence witness against each of those assignments shows it.
    - (∃θ ∈ Θ. ∀φ ∈ Θ′. ¬Agree(θ, φ)) ⇒ ¬Equivalent(A, B)
- A model is subsumed by another when the two are not equivalent and, at every assignment of the parameters either reads, on every input where it is defined, its output is the other's.
    - Subsumed(A, B) ⇔ ¬Equivalent(A, B) ∧ ∀θ ∈ Θ. ∀x ∈ G. Def_A(θ, x) ⇒ A(θ, x) = B(θ, x)
    - A witness shows that a model is not subsumed only where that model is defined.

### Relational form

- An ARC concept relates cells, regions, and their properties.
- A claim has a **relational form** when some set of clauses agrees with the claim on every input the generator produces on which the claim applies.
- A claim that refers to a number that counts nothing the task has, such as a mean or a centroid, has no relational form.
- An **approximation** is a set of clauses that the program runs in place of a rule that has no relational form.
    - The approximation disagrees with the rule on some such input, and that input is a divergence witness.

### Parameterization

#### Invariance

- ARC's symmetry group is generated by the elements of D4 together with color permutations.
- A task transformed by an element of the group is a variant task.
- The model is equivariant.
- When its assignment and input are transformed together, every grid in its output is transformed in the same way.
- Equivariant(M) ⇔ ∀γ ∈ Γ. ∀θ ∈ Θ. ∀x ∈ G. M(γ · θ, γ · x) = γ · M(θ, x)
    - Γ: ARC's symmetry group
    - γ · M(θ, x) = {γ · y | y ∈ M(θ, x)}
- The program is the part of the solver that stays unchanged under the group.
- What a group element changes is task data.
    - Orientations and colors are examples.
- A way of combining content is not task data.
- Models that apply different combining operations to the same content define different families and differ in their clauses.
    - dae9d2b5
    - 3428a4f5

#### Orientation

- Some tasks distinguish a particular direction, axis, or transformation.
- When a task does not distinguish an orientation, neither does the program.
- An **orientation type** is a type that meets each condition:
    - Its full value set is enumerated.
    - Its values remain in the type under the D4 action.
- A mirrored variant task therefore requires a parameter edit rather than a change to the program.
- **Orientation per axis.** A model whose clauses differ between axes does not choose an orientation when one parameter stores the axis on which the clauses are keyed.
- **Every value.** When a membership set meets each condition below, the program enumerates every value of the orientation type, and the parameters are per orientation type rather than per value.
    - It contains every value of an orientation type.
    - No associated data varies by value.
    - No variant task narrows the set.
    - 0ca9ddb6
- **One member.** If one member is used and another must not be used, a parameter stores the chosen member.
- **Another orientation type.** Switching to another orientation type requires another program rather than a reassignment.
    - Switching between cardinal and diagonal directions is one example, and switching between 4- and 8-adjacency is another.
    - a9f96cdd, d364b489
- **Payload.** When values vary from member to member, they are task data, in a relation keyed by the orientation type.
    - d364b489
- **Reassigned set.** A membership set that some variant task narrows is task data, even when it contains every value of the orientation type in the current task.
    - 14754a24

#### Color

- Colors have identity and no other properties.

#### Stored or derived

- Where a stored value fits, the concept case stores structure over colors as a parameter.
    - an ordering
    - a mapping
    - a partition
- Deriving a value asserts that the value depends on the source from which it is derived.
    - **Two parameterizations.** Storing a value and deriving that value produce two different parameterizations.
        - On an input where the derivation gives a value other than the stored one, the stored value agrees with no assignment of the derived model, so they are not equivalent.
        - 3b4c2228
- **Redundant value.** A value that follows from another parameter in every variant task is derived data rather than a second parameter.

#### Open parameters

- The solver stores every open value of an open parameter in one relation, keyed by value.
- open(i) ⊆ Θᵢ: the open values of parameter i
- M_open(θ, x) = ⋂_{v ∈ open(i)} M(θ[i ↦ v], x)
    - M_open: the model read with open(i) in place of θᵢ
- The program runs with every open value of the parameter.
    - The output contains a grid exactly when every open value produces that grid.
        - At those values, the model does not fit a task containing a pair whose accepted output some open value does not produce.
    - 28a6681f

### Cases

- A case is included exactly when it meets each **case condition**:
    - **Fit.** The model fits some split task at its stored assignment.
        - Fit(S_M, T) ⇔ ∃T′ ∈ alts(T). M(stored_M(D(T))) ⊨ T′
        - For a case with an open parameter, only Fit reads the model as M_open at the stored open values.
        - **Unseen key.** When a test uses a key that no train pair contains, a lookup table fails Fit.
            - 1fad071e
            - 3b4c2228
        - Being undefined on another input does not prevent a model from fitting.
    - **Relational form.** Each claim the case's branches replace or add has a relational form.
    - **Equivalence.** The model is not equivalent to the model of another case.
        - Of two cases with equivalent models, the one that takes more non-concept branches fails it, and of two with equal counts, one of them.
    - **Subsumption.** The model of a case other than the concept case is not subsumed by the model of another case.
- For a pair with two candidates, the concept case produces one of them.
- A peer model that produces the other under some assignment is a separate case when it meets the conditions above.
- The pairs leave undetermined which model the task teaches.
- That undetermination is a choice point whose branches are those models.
- The outputs within one candidate introduce no case.

#### Parameters across cases

- **One parameter.** In a task, a parameter admits each value that some assignment gives it while its case fits the task.
    - A collection of case-specific parameters forms one parameter when every task that all of their cases fit admits a value common to every member.
    - Using one parameter across those cases asserts this condition.
    - d23f8c26
    - 5d2a5c43
- **Distinct parameters.** Parameters are distinct when some task that their cases fit admits no value common to them.
    - 87ab05b8

## Encoding

- What holds for the program that encodes a model.

### Definitions

#### Structures and the lib

- **parse**: the structures that a model finds in the input.
- **setup**: the parse shared by every case, together with the clauses that encode it.
- **draft**: a solver that is not yet approved.
- **corpus**: the approved solvers.
- **precedent**: the encoding that the corpus already uses for a structure in the parse.
    - The solver that introduces or improves that encoding establishes the precedent.
    - A precedent covers how the structure is found and encoded.
    - It does not cover the tests performed inside that encoding.
- **component**: a comp declared in a module under `programs/lib/`, or a proposal comp.
- **construction**: a component whose outputs give another form of its inputs.
- **equivariant lib relation**: a lib relation whose output changes under each D4 element exactly as its input does.

### Fidelity

- The program states the task's concept without depending on how the task file or grid encodes it.
- The program states the concept's relations directly.

#### ARC types

- The program works in the task's own types: colors and orientation types.
- A program literal belonging to an ARC type breaks equivariance when the group transforms that value.

#### Numbers

- **Grounding.** Every number in a solver counts concrete things the task has.
    - A distance counts the cells between something and an edge.
    - A size counts the members of a set.
    - A rank counts the members that come before a given member in an order.
- Clause arithmetic expresses a relation.
    - The program states that relation directly.
    - A wraparound shift is a walk around a cycle.
- **Zero is absence.** A `0` counts nothing that is present.
    - In a spatial setting, `0` represents the absence of a gap, offset, or distance.

#### Component instances

- In the program, an instance of a component that is not a construction implements a claim and asserts that the task has that claim.
    - When the task has no such claim, the program expresses the needed step with lib relations or a local clause.
    - That instance may leave any other outputs unused.
- An instance of a construction asserts nothing about the task.

#### Indirection

- A parameter has the form required by the clause or component that uses it.
- **Shared form.** A shared parameter has one form.
    - When the consumers require different forms, each case has its own parameter in the form read by its consumer.
    - 2013d3e2
- A parameter is keyed by objects the program already has.
- A clause used only to translate one representation into another is evidence that one of those representations is unjustified.
    - Naming a position in a 2×2 tile by its corner creates a second name for the same key.
        - a68b268e
    - Routing a flat correspondence through intermediate coordinates introduces another representation.
        - e633a9e5
    - Storing an order as successor edges requires closure to expand it before a comparison.
        - a68b268e
    - A stored map from a tile's places to the sections they fill uses each frame cell as its own key.
    - Storing an orientation as an `Axis`, `Sense`, or `Sym` requires conversion to the `D4` used by the clause.
        - 8ee62060
- Conversion is justified when its two sides differ in content.
    - A sparse set differs in content from its `Ordinal` ranking.
    - A cell set differs in content from its `Canon` class id when the program treats the class as a single thing.

#### Performance

- The principled form is the right form regardless of performance.
- A form chosen for speed comes from constraints of the Datalog implementation and its runner.

### Equivariant lib relations

- An equivariant lib relation preserves the model's equivariance when its inputs derive from parameters, through an atom's arguments or a component instance's `@input` relations.
- A non-equivariant one introduces a hidden orientation into an otherwise symmetric program.
    - Mapping within a tile by distance modulo a period creates a hidden orientation.
        - It is observable unless the extent less one is a multiple of the period.
    - An explicit anchor parameter or an equivariant encoding removes that hidden orientation.
        - 332efdb3

### Corpus consistency

#### Parse priority

- The priorities for choosing a parse are, in order:
    1. Fidelity.
    2. Reuse of facts and component instances already available to the program.
        - 1190bc91
    3. The precedent for the structure.
        - 2dee498d
        - f25ffba3

## Solver file

- What each part of a solver file means.

### File structure

- A solver is one file, `<task_id>.dl`.

    ```
    // <task_id>
    // @draft
    // @keywords: <keywords from keywords.md>
    // @scene <slug>: <what every input contains, as the concept reads it>
    //  <continuation>
    // @rule <slug>: <what the output takes from the input>
    //     @approximated: <the rule the program runs>
    //     @witness <id>: <plausibility> <verdict>

    // <what the choice is>
    .type Choice =
        // @claim <rule or scene slug>
        CaseA {}
        // @scene <slug>: <what this branch changes in the claim, and where it is undefined>
        // @rule <slug>: <what this branch changes in the claim, and where it is undefined>
        // @rule <new slug>: <added claim, and where it is undefined>
        //     @witness <id>: <plausibility> <verdict>
        // @witness <id>: <plausibility> <verdict>
        //     @relaxed <slug of the scene claim this witness breaks>
        //     @reassigned <parameter changed for this witness>
        // @witness <id>: <plausibility> <verdict>
        //     @relaxed <slug of the scene claim this witness breaks>
      | CaseB {}

    .decl out(p: Position, col: Color, ch: Choice)

    .comp Params {
        // @derive <Proposer>: <plausibility> <verdict>
        //     @relaxed <slug of the scene claim this witness breaks>
        .decl bg(c: Color) bg(0).
        // <gloss, where the name does not say what it is>
        .decl recolor(c_fg: Color, c_fill: Color)
        recolor(3, 1).
        recolor(5, 4).

        // --- CaseA ---
        ...

        // --- CaseB ---
        ...
    }

    .init params = Params

    .comp Parse<Key> { ... }
    .init parse = Parse<Unit>

    // shared program clauses

    // <gloss>
    // @claim <slug> <slug>
    .init shape = Components<Unit>

    // @store: <plausibility> <verdict>
    //     @relaxed <slug of the scene claim this witness breaks>
    .decl band(p: Position)

    // @store box: <plausibility> <verdict>
    .init outline = Outlines<Unit>

    // --- CaseA ---
    out(..., $CaseA()) :- ...

    // --- CaseB ---
    out(..., $CaseB()) :- ...

    .comp Determine { ... }
    ```

#### Header

- `@scene` and `@rule` are in dependency order.
- `@keywords` carries the keywords any case claims.
- A `// review <kind>: <text>` line stands last in the header.
- Leave it as it is.
- A family sibling's header, omitting other fields:

    ```
    // <task_id>
    // @draft
    // @representative: <family's first-solved task id> <Case when the sibling has one case of its Choice>
    ```

- A witness under an `@approximated:` line is not `foreign`.
- Each case that runs the approximation has a witness on which its output is not the verdict's.

#### Cases

- A case's model reads its output grids from `out` at that case, one grid per tiebreak resolution, and is undefined on an input where a grid's facts give two frame sizes.
- A case's base is its `Choice` value, its branch at each point the `Choice` encodes; a case is a base with a branch at each `@derive` and `@store` point its base reads.
- A case is witnessed when it is the concept case or stands for a branch's model, or when an input of the task or of the witness file shows it giving an output that no case taking only part of its non-concept branches gives, where undefined counts as an output.
    - The case that stands for a branch's model is that model where the model is a case, and otherwise the case that takes the branch and differs from the concept case at the fewest points.
    - Any other case that takes two branches on which every verdict is `concept` is not witnessed, unless every case that takes one of them also takes the other.
    - On every input of the task and of the witness file, every other case that is not witnessed gives the output of a witnessed case, so a run of the witnessed cases shows each Fit failure it has.
    - Every check, survey and count of `scripts/run_dl.py` runs and reports the witnessed cases alone.
- A branch's clauses are the clauses shared by its cases and absent from the other cases.
- A constructor stands for its branch alone, not for what another branch shares with it, and is named as the Analyze report names the branch.
- `@claim` under the concept branch's constructor denotes the header claim the choice point turns on, which each other branch's `@scene` or `@rule` line changes.
    - A case's reading of a claim is the header's claim with each of its branches' changes made.
- A solver with one case has no `Choice`, case markers, or case column on `out`.
- **Case markers.** Cases do not interleave: each case's Params and clauses are under its marker.
    - Cases that share facts or clauses are under one marker listing names whose cases they are, in the forms the [Witness file](#witness-file) gives, `// --- $Box, $Erode ---`.
    - The comma separates names.
- **`impl_choice`.** The relation that enumerates the cases is `impl_choice`, and its column is `ch`.
    - A record-typed `Choice` gets one enumerator per field a clause enumerates, named for the field's type, as in `.decl locate_choice(l: Locate)`.
    - `impl_choice` contains whole `Choice` values, for a record, as a clause over the enumerators that excludes each combination that is not a case, and it appears when a clause reads one or when the cases are not every combination of the fields.

### Params

- Params contains the parameterization and what derives from it.
- The program reads a parameter as `params.<rel>`.
- `.init helpers = ParamsHelpers` gives the declarations inside Params the shared helpers as `helpers.<rel>`.
    - The program has no access to those helpers.
- A case stores its base's values of each open parameter it stores, and those are that parameter's open values under the case of that base that takes the concept branch at every `@derive` and `@store` point.
    - Of a parameter whose value is a set of rows, a case stores one set.
- **Case column.** Where the cases that read a relation in Params store different values of it, the relation takes a case column in the form of `out`'s, and each fact's case column is the `Choice` value of the case that stores the fact.
    - Each of its facts stands under the marker of the case its case column holds.
- **Empty parameterization.** A task with an empty parameterization keeps the comp empty and the `.init` unchanged: `.comp Params {}`.
- **`@singleton-axis` literal.** A structure that extends along one axis is written in a two-axis type, and the other axis takes a literal `1`.
    - The clause containing that literal ends with `// @singleton-axis: <what the structure is>`.
- **`@derive` directive.** The line is a branch of a choice point on the parameter, at which each case whose base reads the parameter takes a branch and whose concept branch is the stored parameter, with the parameter's value derived by the built-in derivation the line's `<Proposer>` selects; lines on one parameter are branches of one point, and the cases that take one of them are cases of the solver.
    - In a run on an input, a pair's or a witness's, the parameter takes the values the derivation gives on that input; where it gives none, every case that takes the branch is undefined on that input.
    - The verdict `derived` denotes that branch, beside the verdicts a `@witness` line takes, and its witness's id is the branch's name; a further witness of the branch is in the witness file, and the solver has no `@witness` line for it.
    - `// @ignore: derive — <reason>` above the parameter records that every derivation of it fails a case condition, Fit, Equivalence or Subsumption, and no case takes a derived branch of it.
    - `// @ignore: derive <Proposer> — <reason>` above the parameter records the same for the one derivation `<Proposer>` selects.
    - `// @ignore: derive <name> — <reason>` under a `@derive` line records that the cases of `<name>` that take the line's branch fail a case condition, and none of them is a case of the solver.

### Types

- A solver may define:
    - an ADT in `Choice`, in one of these places:
        - as `Choice` itself
        - as the type of a field in the `Choice` record
        - as the type of a field in one or more constructors in `Choice`
    - `TiebreakResolution` for alt outputs
    - a record used as a type argument of a generic comp

### Program

- **`@ignore` directive.** A relation kept despite a hint has `// @ignore: <category> — <reason>` on the line immediately above its declaration, with the category the hint gives.
    - The hint does not fire on the relation.
    - Above a `.init`, `// @ignore <relation>: <category> — <reason>` dismisses that one relation of the instance, and the bare form dismisses every relation of it.
- **`@store` directive.** The relation, or the instance's relation the line names, has one value on every input, and the line is a branch of a choice point on it, at which each case whose base reads the relation takes a branch and whose concept branch is the derived relation, with the relation's value stored per case; the cases that take that branch are cases of the solver.
    - The verdict `stored` denotes that branch, beside the verdicts a `@witness` line takes, with the branch's witnesses named and placed as a `@derive` branch's are; `// @ignore: store — <reason>` and `// @ignore: store <name> — <reason>` record what the `@ignore: derive` forms record.
- **`@workaround` directive.** A temporary workaround is under a `// @workaround: <the principled form it stands in for>` line.
- **`@claim` directive.** At program scope or inside `Parse`, an instance of a component without an `@construction` mark has the directive, one line per instance, listing the claims the instance serves.
    - Each slug denotes a claim.
    - In a family sibling, that claim belongs to the representative's header.

### Components

- **Keys.** Every comp but `Params` and `Determine` takes a `Key` type param.
    - Keyed relations share the key across cases.
    - Single-set sites key on `Unit`.
- **Instance-level inputs.**
    - An input that is the same across cases is part of the instance's identity and takes no key.
    - An input that varies per case is per-key data and keys the comp by the `Choice` fields it varies with.
- **Nested comps.** A nested comp's outputs are read through the instance path.
- **Proposal comps.** A comp outside `Params`, `Determine`, and `Parse` is lib code, and a solver writes one only as a proposal comp, per [Lib addition protocol](docs/handbook/lib-protocol.md).

### Parse

- A `.comp Parse<Key>` contains a derivation that the program and the Determine comp share.

### Determination

- `Determine` contains the determination as one relation per determined parameter, with the parameter's name and schema, derived from `ex_in` and `ex_out`.
- The determination relation of a parameter with a case column gives the rows of every case.
- A determination relation that mirrors no parameter is a helper and takes no parameter's name.
- A derived relation has no determination relation.
- When several determined parameters use an Ident for the same entity, their determination relations derive the same id for that entity. The derived id need not equal the stored id.
- **Test inputs.** A clause that keeps the parameter values that no example contradicts ranges over examples with `ex_out` rows.

### Alt outputs

- A task JSON may give a pair alternate outputs in an alt, whose `kind` states how the outputs differ.
- An alt with kind `rule` gives the pair a second candidate.
- An alt with kind `tiebreak` gives resolutions within one candidate.
- The solver enumerates a tiebreak's resolutions through a trailing `out` column of type `TiebreakResolution`.
- No parameter stores the resolution values.
- No clause treats one resolution differently from another.

### Witness file

- `programs/witnesses/<task_id>.wit.json` holds the witnesses the solver's cases are pinned to.

    ```
    { "id": <task_id>,
      "witnesses": [{
        "id": string,                            // unique within this file
        "separates": string,                     // the feature of the input on which the models differ, and each model's output
        "input": Grid,
        "assign": {<parameter>: Fact[] | Grid | {"grid": Grid, "anchor": [row, col]}},  // the parameters the witness reassigns, which may include a `@store` line's relation
        "output": Group[]                        // when the verdict is not other: one group per distinct output
                | Grid                           // when the verdict is other: the annotator's judged output
      }] }

    Group: { "cases": <name>[],           // the fewest names whose cases together are exactly the cases that give this output
             "grid": Grid | Grid[] | null }  // null for undefined; a list of the grids the cases give, one per tiebreak resolution, when they give more than one
    Grid: number[][]                      // rows of colors
    Fact: Arg[]                           // the arguments of one fact
    Arg: number | string | Arg[]
    ```

- Use a string for a lib constant and a list for a record. Write a constructor with no arguments as a string, such as `"$Anchor"`.
- An `assign` of a relation in [Params](docs/handbook/solver-file.md#params) or of a `@store` line's relation gives its facts without their case part, and every case reads those facts at its own value of the part left out. For a relation in Params, it leaves out the relation's case column. For a `@store` line's relation, it leaves out each column whose type is an ADT in `Choice` or a record built only of such ADTs, and writes a record column that has such fields beside others as the list, in order, of the others. Its key for the relation of a `@store` line above an `.init` is `<instance>.<relation>`.
- [`GRID_HxW` for grid data](docs/handbook/patterns.md#grid_hxw-for-grid-data) states the form of a stored grid.
    - For a parameter that a `GRID_STAMP_HxW` or `GRID_STAMP_SPARSE_HxW` call stores, a grid of the call's size is read as a picture with the `@` on the cell that carries it in the call's layout, and `{"grid": Grid, "anchor": [row, col]}` is read as a picture of any size with the `@` on the cell at that row and column, counted from 0.
- A `<name>` fixes the branch at some choice points, in one of these forms. Its model takes the fixed branches and the concept branch at every other point it takes; its cases are the cases of the solver that take the fixed branches ([Choice points and open parameters](docs/handbook/principles.md#choice-points-and-open-parameters) states both for one branch). A `@witness` verdict names its model; a case marker, an `@ignore: derive` or `@ignore: store` line and a group name its cases.
    - `concept`: the concept branch at every point the `Choice` encodes, the concept base; alone, its model and its one case are the concept case
    - a constructor's name with its prefix, such as `$Alt`: that branch at each point where the constructor stands, for a nested constructor too, whether or not `impl_choice` contains its model
    - `<name> & <name>`: what each fixes
    - `<param>=<Proposer>`, `<rel>=stored`, `<rel>=derived` and `<param>=stored`, each read as a constructor's name: the branch that the `@derive` line on `<param>` with that `<Proposer>` is; the branch that the `@store` line on `<rel>` is; the branch of `<rel>`'s point in which the solver's clauses derive its value; and the branch of `<param>`'s choice point in which its value is stored per case
        - A `<Proposer>` is a component of [proposers.dl](programs/proposers.dl).

## Style

- The conventions a solver file follows.
- Solvers target the latest Souffle.

### Naming

#### Identifiers

- Variables use a single letter with an optional digit suffix, or leading-capital snake_case.
- Macros: SCREAMING.
- Types: PascalCase.
- Relations: snake_case.

#### Position frames

- A Position is named for its coordinate frame.
- **grid** — task input/output frame: `P_grid`. If input and output both appear in one clause, they are `P_grid_in` and `P_grid_out`.
- **tile** — tile-arrangement frame produced by `divide`. `P_tile`.
- **intile** — within a single tile. `P_intile`.
- **inner** — a region's own frame: `P_inner`.
- A Position takes the bare letter where no other frame shares the clause: `P`, then `Q` for a second position.
- A digit suffix tells apart two rows of one relation, as in `placed(D, P1, Q1), placed(D, P2, Q2)`.
- The atom that binds each variable states the frame in its column names.
- `divide` and `tile_pos` name their formal parameters `p_outer` and `p_inner`.
- A solver binds them to `P_tile` and `P_intile` at the call site.
- An axis-only intermediate takes decomposition names such as `P_outer_v` and `P_inner_h`.
- When a decomposition's inner coordinate is also the output cell, the setup decides its name.
- **Fold.** A fold combines the tiles into one output tile.
    - It names the output cell `P_grid_out` in consuming clauses, and keeps `P_intile` in production clauses that decompose the input.
- **Select.** A select of one tile names it `P_intile`.
- **Crop.** A crop to a region's box, using `crop`, names it `P_inner`.
- **Overlay.** An overlay names the frame cell that it stacks onto: `P`, or `P_frame` when another frame shares the clause.

#### Box readings

- A Box column is read as a cell with the `Position` alias, a translation with the `Offset` alias, or a rectangle, margin, or frame change with bare `Box`.
- A comment states a bare Box's reading where the name does not.
- A variable is named for its reading: `B` for a box, `V` for an offset, and `P_rel` for a cell read relative to a box.
- A box is not named `M`.
- "Frame" in a component's name means a frame of cells derived from data, as in `Frame2D`.
- The coordinate-frame sense is stated in prose and Position variable names.

### Header

- `@scene` is only included when `@claim` or `@relaxed` denotes it, the text of a `@rule` or `@approximated:` line depends on it, or a branch replaces it.

### Cases

- **Choice gloss.** The gloss of a choice is above its type, and nowhere else.
- **Other branches.** Every other branch has at least one `@witness` line.
- **Concept branch.** The concept branch is declared first in `Choice`, and in each field's type of a record-typed `Choice`.
- **Branch witness lines.** A witness's nested lines are under the first branch that has it, and a later branch has the `@witness` line alone.
    - A branch nested under a constructor's field states only what differs from the branch it is under.

### Params

- **Shared parameters.**
    - A parameter that every case reads is declared above the case markers, and so are its facts when it has no case column.
    - A parameter that some case never reads goes under the marker of the cases that read it.
- **Derived data.** A clause inside Params writes no value as a literal.
- Facts are not column-aligned across a block.
- **Relative orientation.** If the family fixes an orientation value from another value, the stored form is relative: `Sense` via `turn` and `Axis` via `perp`.

### Types

- [Types](docs/handbook/solver-file.md#types) lists the types a solver may define, and any other type is banned.

### Program

- Program style applies to the Determine comp and to the program clauses other than the clauses of `impl_choice`, of the enumerators, and of the relations that only `impl_choice` and the enumerators read.
- The single-consumer hint also applies to relations in Params.
- The gloss of a relation that carries an `@ignore` directive is in a separate comment immediately above that directive.

#### Bans

- **Literals.** Literals are banned.
    - The program may read `0` and `ZERO` directly.
    - It reads every other lib constant macro, all colors, and non-zero task-shape lengths, offsets, and gaps from Params.
- **Position destructure.** Destructuring a Position is banned.
    - Lib relations read a Position.
- **Arithmetic.** Arithmetic, raw aggregates, and `range` are banned.
    - **Bound comparisons.** A comparison of a distance against a bound is program style, is not arithmetic, and needs no lib relation.
- **`ord`.** `ord` is banned.
    - The lib comp `IdentOf` gives a value its `Ident`.

#### Idioms

- **Complement tests.** The test negates the relation of the values it excludes: `!params.bg(Col)` for non-bg.
- **Off-edge tests.** The test is `!dist(P, D, 0)`.
- **Narrowing.** When a clause binds an argument of a lib relation to a head column of a narrower type, it takes that type's `*_elem` atom.

#### Layout

- [File structure](#file-structure) gives the template, and a file takes its block order and layout from it.
- Related atoms share a line.
- If a line's atoms do not already state what it does, an inline `// ` comment states what the line does.

    ```
    header_color(Idx, Col) :-
        in(P, Col),                                       // input cell
        params.header_dir(D), dist(P, D, 0),              // on the header edge
        params.across_dir(A_dir), dist(P, A_dir, Idx).    // index = across distance
    ```

- **Single-line form.** The single-line form is fine for short clauses (≤ ~80 chars).

#### Disjunction

- A disjunction is conditional branching inside one derivation: the shared frame stated once, then branches split on a test.

    ```
    render(P, Col) :-
        in(P, _), params.side(K), divide_by_size_2d(P, K, 0, P_tile, _),
        ( tile_ink(P_tile, Col)                 // inked tile: one atom tests, grounding Col
        ; !tile_ink(P_tile, _), params.bg(Col)  // blank tile: the test, then Col
        ).
    ```

- Each branch must ground the head's variables on its own.
- A branch that takes a value that the frame already derives binds it with `=`.
- Clauses that share a head and a frame belong in one clause.
- A clause does not range over choice tags through a disjunction.

### Components

- **Proposal comps.** The program-style checks skip a proposal comp.
- A proposal comp with no entry is a hint.
- **Shared comp instances.** A comp instance is shared exactly when its case-specific versions differ only in the case name.
    - A comp instance stays per-case when one case derives a value and another reads it from Params, even when one derivation could feed every case.

## Patterns

- This document records patterns observed across `.dl` solvers.
- A pattern records an encoding that worked, and licenses nothing.
- The `.dl` files are the source of truth.
- Each line below is an entry's title and its first sentence, and `uv run python scripts/context.py section 'Patterns#<title>'` prints the whole entry.
- **Multiple modeling forms via ADT `Choice`** — Multiple models are encoded in one solver file as cases of an ADT `Choice` column on `out`.
- **Choice grounding via `impl_choice`** — If the case column otherwise appears only under negation, a clause shared by all cases needs a positive atom to bind its case variable.
- **`GRID_HxW` for grid data** — A GRID call stores a grid as a literal layout, one fact per cell in row-major order: `GRID_HxW` emits every cell with its value; `GRID_MASK_HxW` and `GRID_SPARSE_HxW` emit the cells that hold something; `GRID_STAMP_HxW` and `GRID_STAMP_SPARSE_HxW` emit those cells as offsets from a marked anchor.
- **`GRID_HxW` catalogs** — A catalog stores several patterns in one id-keyed relation.
- **`RIGID` — parameter relations coupled as a rigid assembly** — A `RIGID` block groups parameter relations stated in one shared intrinsic frame and exposes them only as D4 placements that transform them together, so the stored pose is unobservable.
- **Position remapping via `GRID` id join** — A position correspondence is stored by joining two GRIDs on an opaque id: `src` labels the domain cells; `dst` gives each target cell the id of its source.
- **Tabulated decomposition** — A constant layout is stored as parameter data.
- **Per-tile data keyed by tile position** — Parameter data about one tile of a decomposition is keyed by the tile position that the decomposition produces.
- **Stored total orders as dense ranks** — A total order the output depends on is stored in the parameters as dense rank data and is consumed only by comparison.
- **Set-keyed relations via parent/child tables** — A relation keyed by a multiset of members is represented as two tables joined by an `id`: the parent holds `(id, out-fields)`; the child holds `(id, member-fields)`.
- **Bidirectional mapping via positive recursion** — A symmetric relation is declared in one direction, and `mapping(B, A) :- mapping(A, B)` provides closure.
- **`divide_by_size` (K, G) parameter space** — Different (K, G) splits of one step size model the same periodic layout with different tile/gap semantics.
- **1D `divide` composed to 2D** — `divide` along V and H separately, composed via `compose`, gives 2D decomposition.
- **Wide and long layouts** — A relation can lay co-occurring values out wide, as columns of one atom, or long, as one row per member.
- **Universals via defect negation** — "Every member of a closed domain satisfies R" is stated through a defect witness: one clause derives the keys where some member fails, and the universal is its negation.
- **Open values joined per value** — The program derives the output, or a value the output depends on one-to-one, once per open value, keyed by that value in each case that shares the keyed clauses, and keeps it only where every open value gives the same one, and under tiebreak resolutions the same grid, through any resolution: `Unanimous` over the per-value results, or one `out` clause over every value, where two colors at a cell leave the grid undefined (28a6681f).
- **`cell_split` — input cell with its axis decomposition** — `cell_split` pairs an input cell with its along/across split on the task's axis.

## Keywords

- Keywords index the solvers for a reader who has the headers and not the code.
- A keyword denotes a task concept or a composition property of the program.
- A keyword is admitted when a variant task can carry the concept it denotes, and no listed keyword denotes that concept.
    - A concept narrower than a listed keyword's is admitted when it needs a different parse or rule.
- The mechanism a keyword's gloss states is one instance of the concept the keyword denotes, not the keyword's boundary.

### Setup

- The structure a concept depends on: what the input is and how it decomposes.
- `tile-arrangement` — output arranges transformed copies of the input, or of a piece of it
- `overlay` — content stacks on one frame; panels of a decomposition are one kind of content
- `scale` — content corresponds across a size change
- `decompose` — a separator or division cuts the grid into tiles
- `crop` — a region of the input gives the output its frame or its content, or is the frame the model works in
- `wallpaper` — a periodic pattern covers a region, along one axis or both
- `symmetry` — the model depends on a symmetry of the grid or of a piece of it
- `lines` — the model depends on per-line or per-slice structure
- `objects` — the model depends on discrete pieces of the grid; connected components are one way they are found
- `color-class` — the cells of one color form one unit wherever they lie
- `markers` — designated cells point: they fix a place, direction, extent, or choice, for other content or for the mark itself; a mark may be consumed, and its color may extend along what it designates
- `noise` — stray cells sit among the figure; the model tells them apart, and removes, marks, or ignores them
- `rings` — concentric rings around the frame or a center are the structure, and a cell acts by its ring
- `perimeter` — the grid's border ring is the structure, and content acts by its place along that ring
- `chain` — cells link end to end into one sequence, and the model reads its order along that sequence
- `grow` — the output frame extends the input frame
- `permutation` — elements reorder by a fixed permutation

### Transformation

- The concept the task teaches.
- `lookup` — stored data supplies the output: its content, or where content is read or placed
- `d4` — a D4 transform applies to content
- `congruent` — pieces are identified up to a D4 transform, and the output acts on that identity
- `walk` — stepwise propagation; each step depends on the path or content so far
- `flood` — content spreads from a source through a region until something stops it
- `route` — a fewest-hop route between designated ends through a network of touching pieces
- `cast` — content extends from a source along a line
- `span` — the model depends on an extent delimited by marks
- `bbox` — a unit's bounding box acts as a region: its cells fill, or content places by it
- `depth` — cells act by their distance to the nearest edge of their region
- `enclose` — cells or objects act by whether they are closed off: from the grid edge, from an opening in their wall, or by their neighbors
- `occlude` — content lies in layers, and what shows of a covered thing is a piece of it; the model recovers the hidden part or reads the order of drawing
- `continue` — content leaving one side of a boundary continues on the facing side; the match links the two sides
- `mapping` — a color-to-color relation recolors cells or supplies a fill color
- `count` — a count determines output content, extent, or placement; an extremum over counts is `rank`
- `rank` — an order, a rank, or an extremum determines placement, color, or which piece acts
- `pairwise` — the output holds one entry per pair of the input's items, and the entry says how that pair stands
- `repair` — damaged cells are restored from what the rest of the grid implies; a symmetry or a period gives one set of counterparts
- `classify` — the input, or a part of it, maps to a class; the output renders the class
- `induce` — the input pairs content with the content a rule maps it to, and that rule varies per input; the program reads the rule from those pairs, validates it against them, and applies it beyond them
- `move` — content translates, stacks, or shears within the frame
- `pack` — pieces jointly fill a region exactly
- `stamp` — a footprint stamps at qualifying positions
- `border` — cells act by which side of a border or outline they lie on, or are the drawn outline
- `select` — output keeps or drops a distinguished part of the input
- `parity` — the model depends on even/odd alternation, along a position or along an order
- `cross` — cells where designated lines cross act
- `merge` — like-valued pieces within a task-given proximity fuse into one unit; the output treats the unit as one thing
- `match` — pieces found in the input pair off by a shared property, and the output acts on the pairs; matching against stored data is `lookup`

### Shape

- `latent-canvas` — the program constructs a canvas neither grid fully shows, and the output is determined by that canvas. A canvas is a frame of cells that contains the whole picture in one state.

## Lib addition protocol

- Qualify a new operation for the lib, `programs/lib.dl` and the modules under `programs/lib/`, by real use in the solvers and by generality.
- **Trigger.** Apply this protocol to each kind of operation:
    - A **primitive operation** needs a form the program bans, in any part of its encoding.
    - A **derived operation** is stated in plain relations, and a grep over `programs/solvers/` finds its shape in another solver.
- **Generality.** Treat a proposed operation as general when it states a concept-level relation over a caller-supplied domain and builds in no arrangement beyond the frame.
    - The operation should be as abstract as possible.
    - It involves geometric types only where there is no way to abstract the geometry away.
    - It never involves the Color type.
- **Construction.** The `.comp` line of a proposal comp that is a construction ends with `// @construction`.

### In the pass

1. Write plain program relations that state the lib operation.
    - When cases share those relations, key them.
    - **Proposal comp.** If those relations need a banned form and the concept case reads them, place them in a proposal comp: a `.comp` named for the operation.
        - If the concept case does not read them, write no comp: the branch whose claim needs that form has no set of clauses, and it fails Relational form.
    - **Extension of a lib comp.** Write no comp for an extension of a lib comp. Keep its local clause beside the instance.
    - Run the solver and confirm that the operation works in context.
2. Report the operation: name it, describe it, show the solver-local version, and list the sites the grep found.

### The lib pass

- Runs over the operations the reports list.
- An operation with a proposal comp, or with sites in four or more other solvers, gets an entry.
- The `Match:` line of an entry under [proposals](docs/wf-solver/proposals) is the grep for that entry's operation.

#### The entry

- Give a proposed lib operation an entry, `<name>.md` named for that operation.
- `head -n 3 docs/wf-solver/proposals/*.md` lists every entry's title and first sentence.
- **The entry's fields.** An entry contains:
    - a `# <name> — <operation>` title
    - a first sentence that stands alone
    - the code form, when it has one
    - a `Not:` line stating what is not that operation
    - a `Match:` line with a search signature that covers every statement of the operation, including statements whose atoms are in different lines or clauses, and statements where a solver accesses one lib call only through another
        - state the shape in prose and match it with the parser ([test_ast_match.py](tests/test_ast_match.py))
        - restate a `Match:` line that does not meet this spec
            - a signature that uses an identifier the lib no longer declares, or a header field that [Header](docs/handbook/solver-file.md#header) no longer has, does not meet this spec, and its restatement uses the current name
    - a `Survey:` line per survey, its time to the minute, each followed by its own result
        - the line states the scope the survey covered, as one of these: `Survey: <date time> — every solver.` or `Survey: <date time> — the solvers since <the entry's previous survey time>.`
        - a survey's scope includes drafts
        - the survey result that is relevant to the operation: the near-misses (sites that resemble the operation without stating it), the spec question, and a `Callers` list of the solvers that would call it
            - a citation is the stem and the relation name
        - a survey result is under a `Survey:` line, and the survey command writes the line and that result together
        - text with no `Survey:` line above it counts as no result
        - a survey result stays as written, except for a strike: strike a solver from its `Callers` list when that solver no longer writes the operation, and strike a statement that the entry's current code form, `Not:` line, or `Match:` line contradicts
        - a survey result's spec question is the user's to apply
        - a pass that finds a further site for one lists that site in the review
    - a `Closed: <date time>` line with the judgment, when the operation is closed
- Put in the entry what a reader needs to judge the operation, and nothing else.

##### Removing the entry

- Remove the entry's file at these times:
    - after its callers are migrated
    - at promotion, when the entry lists no callers

#### The sequence

1. Read the entries to find one with the same operation.
    - **Match by operation.** Match by what an operation does, not by its name.
    - When an entry exists, use that entry's name for the comp.
    - Read a solver's proposal comp with its entry.
    - The entry's state decides what to do next.
    - If no entry exists, write one.
        - It has no survey result.
    - If an entry is closed and its judgment rests on a survey result, keep that judgment.
        - Encode the solver without the operation, in the way the entry states.
        - For a closed entry with no survey result, and a closing judgment that requires evidence from the solvers, strike its `Closed:` line and survey the entry.
        - For a closed entry with no survey result, and a judgment that can be made without evidence from the solvers, leave the entry closed.
    - Run the survey again when the pass uses that result for a judgment, including a close.
    - List an unlisted caller in the review, and the next survey lists it.
    - Count a family (`// @representative:` siblings with their representative) as one caller.
    - **The survey.** `uv run python scripts/survey.py <entry>` surveys an entry and writes the survey result into it.
    - Run it when the pass needs an entry's survey result and the entry has none, or some solvers are newer than its newest `Survey:` time.
    - The state sets the scope:
        - the entry has no result: the scope is every solver
        - some solvers are newer than the entry's newest `Survey:` time: the scope is those solvers, as `uv run python scripts/run_dl.py since <time>` lists them for that time
        - the scope's size is no reason to skip the survey
    - If the command fails, spawn the `survey` role with the entry's path, the scope the command would take, and a new directory under your session's scratchpad directory as its scratch path.
        - Append at the end of the entry a blank line, the `Survey:` line in the form the entry's fields give, a blank line, then the role's report.
        - say in the review that the command failed and the role ran
    - If the pass ends with the entry still unsurveyed, say so in the review.
2. Decide whether to close the proposal.
    - **Close grounds.** Base that judgment on whether the operation does not follow principles, or whether it is not general and the solvers encode their tasks without it.
        - The solvers encode their tasks without it when:
            - the lib already provides the operation
            - a plain relation states it and no other solver writes it
            - a relational form replaces the arithmetic
    - **Closing.** When closing a proposal, put the judgment in the entry as the `Closed:` line, remove the proposal comp, and rethink the solver's encoding in relational form.
        - Leave plain relations as written.
        - Write no `Closed:` line before a survey result is in the entry.
        - Include the close in the review as a judgment.
    - **No close.** If the proposal does not close, nothing is decided.
        - Write no text that implies an outcome.
    - **Necessity.** Measure need against the task, not against a case.
        - A comp that serves one case while another case encodes the task without it is not needed.
    - **Not a caller.** Do not count a near-miss as a caller.
        - A lib call that states the proposed operation only over that call's domain is also not a caller.
3. Leave promotion to the user, at the time they choose.
    - The `Callers` list is their evidence.
    - Nothing in the sequence reads its count.
    - [Promote](docs/handbook/procedure.md#promote) states what a pass does at that time.
- **Reimplementations.** A reimplementation states an operation the lib already provides without calling it.
    - An entry lists the reimplementations its surveys found.
- A site is no reimplementation when the lib call would need a value the program bans and no parameter supplies that value.
    - Record it under the entry that states the missing operation, and do not fix it.
- Fix one where it is in a file the pass has open, and strike it from the entry.
- Fix that file even when it has uncommitted edits.
- Leave the rest to the session that opens their files, or to promotion.

#### Changes to existing definitions

- Use the same protocol for changes to existing definitions, such as an edit to a relation or component already in the lib.
- Start such a change at [The sequence](#the-sequence), with the change as what the survey covers.
- The change has no comp form. Write the whole spec in the entry's fields.
- Count as its callers the places the change would benefit.

Reading a component:

- A relation marked `// @input` is one the caller populates, and the facts
  under it are its default. Every other relation derives.

## programs/lib/orders.dl

Components over abstract members whose input carries an order or a step: a
`before` relation, a `succ` relation, or a step count. The members are
opaque, and nothing here reads a position.

The dense rank of each number of a sparse set.

```
.comp Ordinal<Key> {
    // The numbers to rank.
    .decl idx_set(key: Key, k: number)  // @input

    // r = the count of the key's elements strictly less than k, so ranks run
    // ascending from 0.
    .decl rank(key: Key, k: number, r: number)

    // The same count, strictly greater.
    .decl rank_desc(key: Key, k: number, r: number)
}
```

Ranking over members of any type: the caller supplies the strict order,
and the rank of t counts the members before it, ascending from 0.
`before` is read over `elem`, and a row with an endpoint outside `elem`
is ignored. `elem` and `before` may be recursive with `first` and `last`.

Requires: `before` is transitive; it is never closed, so a `before` that
holds direct comparisons alone yields predecessor counts, not ranks.

```
.comp Order<Key, T> {
    .decl elem(key: Key, t: T)  // @input
    .decl before(key: Key, a: T, b: T)  // @input

    .decl rank(key: Key, t: T, r: number)

    // The same count, over the members after t.
    .decl rank_desc(key: Key, t: T, r: number)

    // The element nothing precedes.
    .decl first(key: Key, t: T)

    // The element nothing follows.
    .decl last(key: Key, t: T)

    // b directly follows a: before, with nothing between.
    .decl next(key: Key, a: T, b: T)
}
```

## programs/lib/box.dl

The box algebra: every component whose signature holds a Box, a Position,
or an Offset, and that takes no keyed set of cells as input.

Box is the edge-margin record (t, b, l, r), ordered V-first then H — a
rectangle placed in a frame by its margins from the four edges. A frame of
extent (V, H) reads the record as the rows t..V-1-b and the columns
l..H-1-r; a negative margin reaches past the frame.

The per-axis sum (t+b, l+r) measures the frame's extent minus the
rectangle's, so boxes with one sum are translates of one another. A
Position is a cell, extent 1 on both axes, which carries its frame. An
Offset is a translation, sum 0, which moves any box and keeps its extent.
Every other reading is a Box read against a frame the reader supplies.

The zero box: the whole frame as a box, no move as an offset.

The D4 ops that take one valued cell set onto another. The outputs treat
a missing image cell in two ways: `mismatch`/`map` read it as difference,
so `dst` must be total over each key's domain; `conflict`/`compatible`
compare only where both cells exist, so a partial dst keeps its ops. With
dst = src the maps are the set's symmetries.

```
.comp D4Map<Key, Val> {
    .decl src(key: Key, p: Position, v: Val)  // @input
    .decl dst(key: Key, p: Position, v: Val)  // @input

    // A violated op: some src cell whose image under d holds a different dst
    // value.
    .decl mismatch(key: Key, d: D4)

    // The ops that hold — the negation of mismatch.
    .decl map(key: Key, d: D4)

    // A contradicted op: some src cell whose image holds a different dst
    // value where both cells exist.
    .decl conflict(key: Key, d: D4)

    // The ops dst never contradicts — the negation of conflict.
    .decl compatible(key: Key, d: D4)

    // Invariance under some nontrivial element — the dst = src reading.
    .decl has_sym(key: Key)
}
```

Translation invariance of a valued cell set: which axis-aligned
translations fix the set. Absence is silent: an image off the frame tests
nothing, so a translation is compared only where both cells exist. Two
readings: `mismatch` is exact; `period` reads through sparse damage.

```
.comp OffsetInvariance<Key, Val> {
    .decl cell(key: Key, p: Position, v: Val)  // @input

    // Candidate translations: every axis-aligned one the frame admits, tagged
    // (axis, k), with both directions of a magnitude sharing a tag.
    .decl cand(key: Key, a: Axis, k: number, delta: Offset)

    // A candidate translation's cell pairings: q is p's image, both in the set.
    .decl pair(key: Key, a: Axis, k: number, p: Position, q: Position)

    // A violated translation: some cell whose image holds a different value.
    .decl mismatch(key: Key, a: Axis, k: number)

    // A broken line pair: the translation carries some cell of the line at l
    // onto a differently-valued cell of the line at l2.
    .decl line_mismatch(key: Key, a: Axis, k: number, l: Position, l2: Position)

    // A period of the set's pattern, read through damage: broken line
    // pairs do not outnumber whole ones. Every multiple of a period is a
    // period, and a pair-less candidate is vacuously one.
    .decl period(key: Key, a: Axis, k: number)

    // The exact reading's minimum: the shortest witnessed translation no cell
    // pair contradicts, per axis.
    .decl min_period(key: Key, a: Axis, k: number)
}
```

## programs/lib/constraints.dl

Components over pieces and candidates the caller supplies as opaque labels,
together with a `conflict` relation over them, and the enumeration of a
tiebreak's resolutions.

The pieces every exact cover of a keyed cell set must contain, found by
elimination: a cell with one candidate piece left forces that piece, and a
piece that overlaps or conflicts with a forced piece is ruled out.
Elimination starts only at a cell with one candidate left, so `forced`
can be partial, also on an input with one exact cover. An output built
from a partial `forced` has missing cells and no wrong cell. Forced pieces
that are not ruled out are pairwise disjoint. With a single footprint,
`forced` is the greedy tiling in reading order.

```
.comp CoverForcing<Key, Piece> {
    // The candidate pieces and the cells each covers.
    .decl covers(key: Key, piece: Piece, p: Position)  // @input

    // Two pieces that no cover holds together, apart from overlap.
    .decl conflict(key: Key, piece: Piece, piece2: Piece)  // @input

    // Some cell has no other candidate piece.
    .decl forced(key: Key, piece: Piece)

    // Overlaps or conflicts with a forced piece.
    .decl ruled_out(key: Key, piece: Piece)
}
```

The candidates a joint placement of the pieces can still hold, found by
refutation. A candidate is refuted when some other piece has no candidate
compatible with it, or some pair of other pieces has no compatible pair
beside it. `alive` over-approximates: every candidate of a joint placement
survives, so an output built from the survivors has missing cells where
surviving candidates disagree and no wrong cell, as long as every piece
has a candidate. A piece takes at most one candidate. A piece with no
candidate refutes nothing; the caller checks for that case. Each
candidate belongs to one piece: a key with a candidate under two pieces
gets no `dead` and no `alive` row.

```
.comp PlacementPruning<Key, Cand, Piece> {
    // The candidate placements of each piece.
    .decl cand(key: Key, c: Cand, o: Piece)  // @input

    // Two candidates no joint placement holds together.
    .decl conflict(key: Key, c: Cand, c2: Cand)  // @input

    // The refuted candidates.
    .decl dead(key: Key, c: Cand)

    // The candidates not refuted, with their pieces.
    .decl alive(key: Key, c: Cand, o: Piece)
}
```

The resolutions of a tiebreak: every injective assignment of candidate
items to slots, one term per assignment, backing a TiebreakResolution out
column. Constructor names are program-global, so the solver declares the ADT
the comp constructs:

  .type TiebreakResolution =
      End {} | Sit {slot: Slot, item: Item, rest: TiebreakResolution}

```
.comp TiebreakResolutions<Key, Slot, Item> {  // @construction
    // The candidate items of each slot.
    .decl cand(key: Key, slot: Slot, item: Item)  // @input

    // The valid assignments: no item used twice.
    .decl resolution(key: Key, res: TiebreakResolution)

    .decl assign(key: Key, res: TiebreakResolution, slot: Slot, item: Item)
}
```

# Code reviewer

- Main is the session that launched you, and your final message goes to it.
- Edit nothing under the tree other than the issues you file.
- When you start, record the tree as this scan's baseline, untracked files under `src/`, `scripts/` and `tests/` included, with this scan's number as `<n>`, in one Bash call:

    ```
    export GIT_INDEX_FILE=<scratch directory>/index && git read-tree HEAD && git add -A src scripts tests && git tag scan/<n> $(git commit-tree $(git write-tree) -p HEAD -m scan<n>)
    ```

- Read each baseline, this scan's included, through `git worktree add` on its tag, in your scratch directory, and remove each such worktree with `git worktree remove` when you are done.
- Run no other git command that changes state.
- Diff `src/`, `scripts/` and `tests/` of the earlier baseline against `scan/<n>`.
- Find every place in the diff of each kind below.
- Judge each defect place: whether it is a defect, and where it is one, whether it stands.
- Leave out a place that an earlier `refactor` or `undecided` issue cites, unless that issue was resolved `fixed`.
- File each defect as an issue of kind `refactor`, and each place that poses a question as an issue of kind `undecided`, with `scan<n>` as `<source>` and `code-reviewer` as `<agent>`.
    - Cite each place as [Place issues](#place-issues) gives.
    - Resolve the issue of each defect place that stands.
- Then end your turn with a message to main of at most six lines: the pattern that matches the names of the issues you left under `issues/new/`, and the count of issues under each kind of place.

## Working rules

- Read nothing under `../arc-synth-bun/`.
- Launch no agents.
- Keep `progress.md` in your scratch directory, with your start time, what is done and what is next. After your context is compacted, read it before anything else.
- When your time since the start passes one and a half times your estimate, write what is done and what is left in `progress.md`, and end your turn with a message to main that says the estimate is passed.
- Run each command in the foreground, with a timeout of 600000 ms on the Bash call.
- End your turn only once each command you started has finished, even where a hook that blocks a wait tells you to end it.
- Where the harness moves a command to the background, wait in a foreground Bash call with a timeout of 600000 ms, whose until-loop gives up just under that timeout, and repeat the call until the command's completion notification has arrived.
    - Lead its command with `: 'unattended-wait: <the command you wait on>, since a turn that ends while it runs ends my run';`.
    - Loop on the completion where you can observe it, and otherwise on the time alone.

## Issues

- Where your instructions, your brief or a later message ask you to file an issue, file it with `uv run python scripts/file_issue.py`, in the form its `--help` gives.
    - Where no other line gives them, `<agent>` is your agent's name, and `<source>` is a short name for your work.
    - Where no other line gives an issue's kind, give it one of these:
        - `interference`: something in your output was wrong because of the issue, whether or not you repaired it.
        - `delay`: the issue cost time or tokens only.
        - `undecided`: a case your rules do not cover, or a place that poses a question.
    - Write under `Evidence` the line quoted, or the command and its output, or the grid, as you saw it.
    - Leave out what the fix should be.
- The directories `issues/new/`, `issues/assigned/` and `issues/resolved/` are an issue's statuses, and moving its file between them is its transition.
- After each transition, append a line to the file's log, in the form `<time> <status> [<agent>]: <note>`, with your agent's name as `<agent>`.
    - Write the log as the file's last section, `## Log`, and add that section with its first line.
    - Lead the note of the line into `resolved` with the resolution: `fixed`, `duplicate`, `cannot-reproduce`, `wontfix` or `invalid`.
        - The resolution of a place that is judged and kept is `wontfix`, and the note gives the judgment.

## Place issues

- Cite a place's target as every location of the place. For one idea in two places, the locations include those outside the diff.
- Write under `Effect` what the code does there, and quote each location under `Evidence`.
- In the title of an `undecided` issue, write the question it poses after the target, in place of what is wrong in it.

## Kinds of place

- Defects:
    - One idea in two places: a computation, selection, rule, rendering or sentence written twice, in one module or across modules.
    - Solver text read or written outside the `souffle` package.
    - A lookup that defaults where the value could be unknown, or a closed vocabulary held as `str`.
    - An iteration whose order reaches output, run in hash order.
    - A value that crosses a package boundary as a string the other side parses.
    - A test that [Tests](CLAUDE.md#tests) does not keep.
    - Prose in code that breaks a rule of [Prose in code](src/controlled_markdown/writing.md#prose-in-code).
    - A name the diff gives a thing, where practitioners of the thing's discipline use a conventional name for it that the diff does not use.
- A defect place stands, with its reason, where a package boundary forces the second copy, where a rule requires it, or where an absent value has a known meaning.
    - Each check quotes for itself the handbook passage it rests on, so one passage quoted at several checks stands.
- Places that pose a question:
    - A condition on one solver, one command or one shape of input.
    - A change in the diff that makes false the premise of any line but its own lines, in a document or in prose in code.
